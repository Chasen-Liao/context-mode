# Deviations

One row per place a doc was silent and a module file's Assumptions did not close it. Smallest rule consistent with the docs, recorded here so no later reader guesses.

| Date | File | Question | Decision | Reason |
|---|---|---|---|---|
| 2026-10-17 | `e2e/harness/hook-runner.mjs` | 14-tests.md §1/§4 names `hook-runner.mjs` and its purpose ("spawn hook entry, capture stdout/exit/ms") but no export signature. | `e2e/cases/GP3-hooks.e2e.mjs` imports `runHookFixture(hookBundlePath, agentId, payload): Promise<{ exitCode, stdout, ms }>`, matching `mcp-client.mjs`'s documented `spawnBundle`/`McpClient` naming style. | `mcp-client.mjs` (§2) is the only harness file with a written signature; `hook-runner.mjs` is owned by a later step, so T0 picks the closest-named shape rather than leave the import unresolvable, and records it for that step's implementer. |
| 2026-10-17 | `e2e/live/cases/*.json` (`kind: "local"`) | `LiveCase.expect` for `kind: "local"` names `jsonField`/`equals` but no doc fixes what JSON shape a `run` script must print. | Every `kind: "local"` check script in this module (`e2e/checks/*.mjs`, and the eventual `e2e/cases/run.mjs --milestone` JSON summary) prints exactly one JSON line `{ ok: boolean, ... }` to stdout and exits 0 regardless of `ok`; the four M0 live cases use `expect: { jsonField: "ok", equals: true }`. | 14-tests.md §6 fixes the `LiveCase` interface but not the convention a `run` script follows; one shared `{ ok }` line is the smallest rule that lets `run.mjs`'s local branch parse any of this module's check scripts the same way. |
| 2026-10-17 | `e2e/golden/GP1/*.json` | 14-tests.md §4 step 4-6 fixes the golden-compare mechanism but not which fields of a GP1 case's collected value belong in its golden file. | Each GP1 golden file holds only the fields this spec's text already names for that case (`toolNames` for harness-smoke; `hasPackageJson`/`hasNodeModules`; `matchCount`; `errorModuleNotFound`) — no extra captured fields. | Keeps the golden file a direct, auditable encoding of the case's own "Given/When/Then" text (14a-issue-cases.md) rather than an implementer re-deriving extra shape later. |
| 2026-10-17 | `scripts/gate.mjs` (D-M0-1) | When does each gate layer start, and what does a layer print before it starts? Docs name the layers (impl/14 §8, impl/13 §7, impl/15 §2) but no start milestone. | Start milestones: keep-pass M0, gp-cases M0, prompt-lint M0 (drafts mode) and M2 (bundle mode `--out release-out`), check-removed M6, live M0. Before its start a layer prints `SKIP <layer> starts at Mn`. At or after its start, a missing script is `FAIL`, never `SKIP`. After the first `FAIL`, later layers print `SKIP <layer> not run: <layer> failed`, so the output has one line per layer. | check-removed would fail on every v1 file the 131 KEEP-PASS tests still need (impl/15 §2 list includes `vitest.config.ts`, `src/cli.ts`); those files go only at the deletion gate (TECH-SPEC §6.8). One line per layer keeps `e2e/live/cases/gate-layers.json` deterministic. |
| 2026-10-17 | `e2e/cases/*.e2e.mjs`, `e2e/cases/run.mjs` (D-M0-2) | impl/14 §5 does not say how `run.mjs` picks the cases for a milestone. | Each `node:test` name starts with the tag `[Mn] ` (for example `[M0] GP1/harness-smoke`). `run.mjs --milestone Mn` runs only the tests whose tag is `<= Mn`; without the flag it runs all. | One literal prefix in the test name is the smallest rule; it needs no extra file and the gate passes the milestone it was given. |
| 2026-10-17 | `.impl/keep-pass-baseline.json` (D-M0-3) | Some of the 131 KEEP-PASS files can be red on v2-design before their owning module is rebuilt. Must they fail the gate at once? | Optional file `.impl/keep-pass-baseline.json` = JSON array of KEEP-PASS paths that are red today. The gate runs them and reports them (`baseline red (not due)`), but they fail the keep-pass layer only from the milestone of their owning module (`.impl/keep-pass-map.json`) on. A path not in the map is a `FAIL`. | ADR-0003 r2 keeps the files; this keeps them visible without blocking milestones that do not own them. The list can only shrink: a module's milestone gate makes its rows hard. |
| 2026-10-17 | `e2e/harness/*` (D-M0-4) | Harness exit timeout: the constant lives in `src/core/contracts/constants.ts`, but files under `e2e/` must not import `src/` (GS4). | `e2e/` uses the literal `2000` ms, with a comment naming the constant it mirrors. | GS4 import ban wins over the one-constant-file rule for test code; the literal is checked by GP9 behavior, not by import. |
| 2026-10-17 | `docs/v2/impl/14a-issue-cases.md` (D-M0-5) | 14a lists cases by GP id, not by milestone. Which milestone writes each case? | A 14a case gets the milestone that builds the code under its `covers` path. M0 writes only the GP1 harness/bundle cases and the GP3 fixture replay; the other GP1/GP3 14a cases are written in M2, M3 and M5. | A case for code that does not exist yet can only fail; tagging by the owner milestone keeps each gate green-able. |
| 2026-10-17 | `src/core/contracts/*` (D-M0-6) | TECH-SPEC §12 puts contracts in M1, but the M0 build and harness need types and constants. | The contracts module (`types.ts`, `constants.ts`, `errors.ts`, `agents.ts`) is written in M0. | The M0 bundle and hook skeleton import them; writing them later would need a temporary copy, which the one-constant-file rule forbids. |
| 2026-10-17 | `src/entries/hook.ts` (D-M0-7) | M0 needs a hook entry for the GP3 fixture replay, but policy is M3. | M0 hook entry is a decode -> allow -> encode skeleton with no policy; M3 replaces it. | Smallest code that lets GP3 assert exit 0 and the native stdout shape. |
| 2026-10-17 | `build/build.mjs` (D-M0-8) | impl/13 §2 lists 5 entries (server, hook, run, pi, opencode); only server and hook exist in M0. | `build.mjs` builds only the entries that exist in M0 (server, hook). The milestone that writes `run-wrapper.ts`, `pi.ts`, `opencode.ts` adds their rows. | No fallback or "skip if missing" branch in the build; each row is added with its source file. |
| 2026-10-17 | `.impl/keep-pass-map.json` (D-M0-9) | Where does the KEEP-PASS file -> owning module map live? | `.impl/keep-pass-map.json` holds `moduleMilestone` and `files: {path: {module}}` and is used only by `scripts/gate.mjs`. `tests/keep-pass.list.json` stays the single GS4 source (impl/14 §7). | Keeps the GS4 list unchanged; the map is workflow data, not a product input. |
| 2026-10-17 | `.github/workflows/ci.yml` (D-M0-10) | impl/13 §8 runs bare `npx vitest run`; DECISIONS-r9 G5 fixes the command; impl/13 §8 triggers only `main, v2`. | ci.yml runs `npx vitest run --config tests/vitest.config.ts` and adds `v2-design` to the push branches. | The later DECISIONS file wins (G5); bare `vitest run` would pick up v1 `vitest.config.ts` and non-KEEP-PASS files. `v2-design` is the branch the work lands on. |
