## Why this matters for the v2 rule

v1's Read branch was hint-only by construction, not by a reasoned trade-off against breaking Read-before-Edit — issue #1267 is a bug report that the hint provides no backpressure, not a design note defending the choice. No issue in `tickets/data/isall.json` argues a Read deny would break edits; the risk is real but undocumented, which is why v2's T3 threshold ("0 needed reads blocked with no working path") is enforced structurally: any Read with `offset`/`limit` is always allowed, so a size deny on the unranged call never removes the only path to the bytes an Edit needs.
